# CHANGELOG — B8-04

## R5 — текущий

- Добавлены два сценария на одноразовом PostgreSQL с отдельными процессами и барьерами в базе.
- STOP, который первым держит scoped lock, доводится до commit только после подтверждённого ожидания подготовки. Подготовка получает `BLOCKED` и не оставляет staging, save, proposal или replay.
- Подготовка, которая первой держит lock после dispatch, фиксирует свою транзакцию. Ожидающий STOP не отменяет уже зафиксированное. После его commit новый запрос получает `BLOCKED` без новых эффектов.
- Порядок доказан событиями барьеров, `pg_stat_activity`/`pg_locks` и чтением из отдельного соединения. Использованы ограниченные таймауты и принудительное завершение дочерних процессов.
- Архив собран стандартным `zipfile`: одна корневая папка `B8-04_RETURN_FINAL_R5`, имена через `Path.as_posix()`.
- Документы больше не называют R3 или R4 актуальным возвратом.

Поведение `api.py` не переписывалось: дефект в уже исправленной финальной проверке не обнаружен.

## R4 — исторический

- После `dispatch.propose` и до commit повторно читаются authority и каталог.
- STOPPED/HUMAN/HANDED_OFF даёт `BLOCKED`; смена version/revision даёт `STALE`.
- Отказ выходит исключением и откатывает эффекты текущей транзакции.
- Были crash-before/after-commit и сценарий, где STOP завершался до подготовки, а конкурентно проверялась смена каталога.

## R3 — исторический

- Первый собранный возврат исполнителя до исправления финальной проверки после dispatch.
